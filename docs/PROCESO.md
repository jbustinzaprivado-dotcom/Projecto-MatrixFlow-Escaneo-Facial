## 1. Reglas de trabajo (acordadas)

1. Ninguna decisión queda al azar. Todo lo ambiguo se consulta antes de actuar.
2. Cada elemento se etiqueta **[PDF §n]** si viene del documento o **[Añadido]** si es una funcionalidad extra acordada fuera del documento.
3. Se trabaja el **frontend primero** (con datos simulados), luego el backend, igual que en el proyecto de referencia.
4. Al cerrar cada fase se emite un informe que documenta todo lo realizado hasta ese momento.
5. No se genera código ni proyecto hasta que el equipo lo autorice de forma explícita, fase por fase.
6. Ninguna decisión se borra: si una corrige a otra, queda anotado cuál corrige y por qué.

## 2. Por qué existe este proyecto (contexto, no forma parte del documento)

Este desarrollo tiene doble propósito: es la entrega académica del documento fuente (la nota depende de qué tan bien se entendió y desarrolló el documento) y, a la vez, sirve de base para un conjunto de funcionalidades que luego se llevarán a un proyecto real de una empresa (un dashboard de estudiantes, hecho en PHP, fuera de este repositorio). Por eso se construye con el mismo estándar de un sistema en producción (pruebas, seguridad, manejo de errores), aunque el que realmente se despliegue sea el otro proyecto.

> **D31 (corrige el criterio guía de D4, sin borrarlo):** a partir de la Fase 3, el objetivo de reutilización en la empresa queda **en segundo plano**. Lo que guía cada decisión de aquí en adelante es la fidelidad estricta a la estructura del documento fuente — no lo que convendría para el otro proyecto. D4 sigue siendo cierto (el propósito dual no desaparece), pero deja de ser el criterio con el que se resuelve una ambigüedad.

## 8. Fase 4 — Motor matemático Python + NumPy

**Estado: cerrada.** El módulo `algorithms/` **[PDF §11]** ya calcula de verdad; `operation_service` deja de responder `"pendiente"`.

| # | Tema | Decisión |
|---|---|---|
| D38 | Las 10 funciones exactas del documento | `algorithms/vector_ops.py` (§11.1: `sum_vector`, `subtract_vector`, `scalar_multiply`, `dot_product`), `algorithms/matrix_ops.py` (§11.2: `add_matrix`, `subtract_matrix`, `multiply_matrix`, `transpose_matrix`, `scalar_multiply_matrix`) y `algorithms/linear_algebra.py` (§11.3: `linear_combination`, más `validate_vector`/`validate_matrix`/`validate_dimensions`, repartidas en el archivo de vectores o de matrices según a quién validan). | D39 | Corrección de un bug arrastrado: `combinacion_lineal` con un solo escalar | Desde la Fase 2, el esquema pedía un único `escalar` para `combinacion_lineal`, pero esa operación es `c1·A + c2·B` — necesita **dos** coeficientes, uno por vector, no uno solo. Se corrigió agregando `coeficiente_a` y `coeficiente_b` al esquema (D30), manteniendo `escalar` solo para `escalar_vector`/`escalar_matriz`. Encontrado al implementar el cálculo real, no antes. |

El servicio ahora solo atrapa `DimensionError` y decide `estado: "error"` — la regla matemática vive en un solo lugar. |
| D41 | Sin pytest todavía | El documento asigna las pruebas automatizadas a la **Fase 8** (§15), no a esta. Se verificó cada función con un script manual (`venv/bin/python -c "..."`, con resultados calculados a mano) y con curls reales contra el servidor — sin crear una carpeta `tests/` todavía, para no adelantar otra vez el trabajo de una fase futura. |
| D42 | Verificación de la Fase 4 | Script manual: las 10 funciones dieron el resultado matemático correcto (comprobado a mano) y las dos funciones de multiplicación/suma con dimensiones incompatibles lanzaron `DimensionError` como se esperaba. ## 24. Correcciones de una auditoría de código [Añadido]

**Estado: cerrado.** Antes de escribir el informe final de sustentación, el equipo pidió una revisión profunda de todo el proyecto buscando errores graves. Se encontraron 4 problemas reales (verificados contra el código, no solo sospechas); se corrigieron los 2 graves de inmediato, los 2 menores quedan documentados como limitación conocida.

| # | Tema | Decisión |
|---|---|---|
| D137 | Bug no relacionado, encontrado al verificar D128: `MODELS_DIR` del motor facial apuntaba mal | `backend/app/services/biometria/face_engine/engine.py` calculaba la carpeta de los pesos ONNX contando niveles de carpeta padre (`parents[3]`). Cuando el motor se movió de `services/face_engine/` a `services/biometria/face_engine/` (reorganización de carpetas, sección 22), ese conteo quedó desactualizado: apuntaba a `backend/app/models/` (el paquete de modelos SQLAlchemy) en vez de `backend/models/` (donde van los `.onnx`, D45). Corregido a `parents[4]`. Sin relación con la funcionalidad de ubicación — solo salió a la luz porque se hizo login real para probarla. |
| D138 | Grave — limitador de `/verificacion` roto detrás del proxy de Render | El límite de "10 intentos por minuto" se guarda por IP (`request.client.host`), pero el `Dockerfile` levantaba `uvicorn` sin `--proxy-headers`: detrás del balanceador de Render, toda petición le llega a la app con la IP interna del proxy, no la del usuario real — el límite por IP se volvía, en la práctica, un único cupo compartido por todos los usuarios del sistema a la vez. Corregido agregando `--proxy-headers --forwarded-allow-ips='*'` al `CMD` del Dockerfile (el contenedor, en Render, solo es alcanzable por el proxy de Render — confiar en el header que agrega es seguro). Es el único endpoint sin sesión de todo el backend, así que era el punto donde más importaba. |
| D139 | Grave — una venta no descontaba el inventario | `sale_service.create_venta` y `inventory_service.registrar_movimiento` eran dos caminos totalmente independientes: se podía vender cualquier cantidad de un producto con existencias en 0, y el Dashboard/Reportes mostraban cifras de ventas sin relación real con el stock. Corregido: `create_venta` ahora reutiliza las mismas funciones de `inventory_repository` que ya usa `registrar_movimiento` (`get_or_create`, `add_movimiento`, `ajustar_existencias`), con el mismo criterio de "no existencias negativas" (422 si no alcanza el stock). El cambio es hacia adelante: no recalcula el inventario de las ventas ya sembradas por `seed.py`, que escribe directo a las tablas sin pasar por este servicio. |
| D140 | Menor, documentado sin corregir | **Condición de carrera en el control de stock negativo** (`inventory_service.registrar_movimiento`): la validación lee `existencias` y luego escribe sin bloqueo de fila — dos salidas simultáneas sobre el mismo producto/sucursal podrían, en teoría, dejarlo en negativo. Poco probable con un solo operador a la vez (uso real del sistema), se documenta como limitación conocida en vez de agregar bloqueo pesimista sin que nadie lo haya pedido. |
| D141 | Menor, documentado sin corregir | **Metas y movimientos de inventario no validan que la sucursal/producto existan** antes de insertar, a diferencia de Ventas (que sí lo hace y devuelve un 404 limpio) — con un id inexistente, el error llega como un 500 crudo de PostgreSQL en vez de un mensaje claro.
